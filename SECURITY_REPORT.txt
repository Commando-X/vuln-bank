2. AS 6 VULNERABILIDADES CRÍTICAS QUE EXIGEM AÇÃO IMEDIATA
   ──────────────────────────────────────────────────────────────────────

   ┌─ #1 ─────────────────────────────────────────────────────────┐
   │ Vazamento de PAN + CVV em endpoints de pagamento              │
   ├──────────────────────────────────────────────────────────────┤
   │ Arquivo:   merchant_payments.py                              │
   │ CWE:       CWE-312 (Cleartext Storage of Sensitive Info)     │
   │ Severidade: CRÍTICA                                        │
   │ Detectado por: OCR (MiniMax-M3)                              │
   ├──────────────────────────────────────────────────────────────┤
   │ O QUE ACONTECE:                                              │
   │ Quatro endpoints da API merchant retornam o número completo  │
   │ do cartão (PAN) e o código de segurança (CVV) nas respostas │
   │ JSON. Isso viola o requisito 3.2 do PCI-DSS, que proíbe o  │
   │ armazenamento ou retorno do CVV após autorização.             │
   │                                                              │
   │ POR QUE IMPORTA:                                             │
   │ Qualquer merchant que consuma esses endpoints acaba gravando │
   │ dados de cartão em seus próprios logs de aplicação. Em caso  │
   │ de vazamento desses logs, o impacto cascateia para todos os  │
   │ clientes da plataforma.                                      │
   │                                                              │
   │ COMO CORRIGIR:                                               │
   │ Remover os campos `card_number` e `cvv` de todas as respostas.│
   │ Quando necessário, retornar apenas os últimos 4 dígitos do  │
   │ PAN. Adicionar `?fields=card_number&cvv=never` na validação.│
   └──────────────────────────────────────────────────────────────┘

   ┌─ #2 ─────────────────────────────────────────────────────────┐
   │ Bypass completo de autenticação JWT                          │
   ├──────────────────────────────────────────────────────────────┤
   │ Arquivo:   auth.py                                            │
   │ CWE:       CWE-347 (Improper Signature Verification)         │
   │ Severidade: CRÍTICA                                        │
   │ Detectado por: OCR (MiniMax-M3)                              │
   ├──────────────────────────────────────────────────────────────┤
   │ O QUE ACONTECE:                                              │
   │ Três falhas combinadas permitem que um atacante forje tokens │
   │ de admin válidos:                                            │
   │                                                              │
   │   1. auth.py:29  — JWT assinado com segredo literal          │
   │                    "secret123" dentro do código-fonte         │
   │                                                              │
   │   2. auth.py:47  — Quando a verificação falha, o código     │
   │                    decodifica o token SEM validar a assinatura│
   │                    (verify_signature=False). Token forjado é  │
   │                    aceito.                                    │
   │                                                              │
   │   3. Algoritmo `none` aceito na lista de algoritmos permitidos│
   │                                                              │
   │ POR QUE IMPORTA:                                             │
   │ Um atacante pode gerar tokens JWT válidos sem conhecer o    │
   │ segredo. Isso significa controle total sobre qualquer sessão│
   │ de qualquer usuário, incluindo administradores.              │
   │                                                              │
   │ COMO CORRIGIR:                                               │
   │ a) Carregar o segredo de variável de ambiente, recusar       │
   │    iniciar se não definido.                                  │
   │ b) Remover o fallback verify_signature=False — assinatura     │
   │    inválida deve retornar 401.                               │
   │ c) Restringir algorithms=["HS256"] apenas.                    │
   └──────────────────────────────────────────────────────────────┘

   ┌─ #3 ─────────────────────────────────────────────────────────┐
   │ Race condition TOCTOU na transferência de fundos              │
   ├──────────────────────────────────────────────────────────────┤
   │ Arquivo:   auth.py (linhas 185-191)                           │
   │ CWE:       CWE-362 (Race Condition)                          │
   │ Severidade: ALTA (explorável em segundos, mas requer concorr.)│
   │ Detectado por: OCR (MiniMax-M3)                              │
   ├──────────────────────────────────────────────────────────────┤
   │ O QUE ACONTECE:                                              │
   │ O fluxo de transferência faz:                                │
   │                                                              │
   │   SELECT balance FROM users WHERE id=?  -- lê o saldo        │
   │   ... comparação no código Python ...                       │
   │   UPDATE users SET balance = balance - ? WHERE id=?        │
   │                                                              │
   │ Entre o SELECT e o UPDATE existe uma janela onde múltiplas │
   │ requisições concorrentes podem cada uma ler o mesmo saldo,    │
   │ passar na verificação, e executar o débito.                  │
   │                                                              │
   │ POR QUE IMPORTA:                                             │
   │ Atacante com 10 threads pode multiplicar R$ 100 em R$ 1000, │
   │ ou deixar saldo negativo. Em SQLite, essa janela é ainda    │
   │ maior porque as escritas são serializadas mas em transações    │
   │ separadas.                                                   │
   │                                                              │
   │ COMO CORRIGIR:                                               │
   │ Unificar em um único UPDATE condicional:                      │
   │   UPDATE users                                               │
   │   SET balance = balance - ?                                  │
   │   WHERE id = ? AND balance >= ?                              │
   │ Se rowcount=0, abortar a transferência.                       │
   └──────────────────────────────────────────────────────────────┘

   ┌─ #4 ─────────────────────────────────────────────────────────┐
   │ API keys de merchant previsíveis (10.000 possibilidades)      │
   ├──────────────────────────────────────────────────────────────┤
   │ Arquivo:   merchant_payments.py                              │
   │ CWE:       CWE-338 (Cryptographically Weak PRNG)            │
   │ Severidade: CRÍTICA                                        │
   │ Detectado por: OCR (MiniMax-M3)                              │
   ├──────────────────────────────────────────────────────────────┤
   │ O QUE ACONTECE:                                              │
   │ As API keys são geradas assim:                                │
   │                                                              │
   │   api_key = f"vk_{hashlib.sha256(str(random.randint(0,9999))│
   │             .encode()).hexdigest()[:32]}"                   │
   │                                                              │
   │ Existem apenas 10.000 valores possíveis de entrada. O hash │
   │ SHA-256 é determinístico. Um atacante que conheça o esquema │
   │ pode enumerar offline todas as 10.000 chaves e testar       │
   │ contra a API em segundos.                                   │
   │                                                              │
   │ POR QUE IMPORTA:                                             │
   │ Qualquer merchant com chave válida pode fazer requisições    │
   │ em nome de outro merchant — cobranças, listagens, refunds.   │
   │                                                              │
   │ COMO CORRIGIR:                                               │
   │ Usar secrets.token_urlsafe(32). Cada chave terá 256 bits de  │
   │ entropia real, impossível de enumerar.                       │
   └──────────────────────────────────────────────────────────────┘

   ┌─ #5 ─────────────────────────────────────────────────────────┐
   │ 33 pontos de SQL Injection via concatenação de strings       │
   ├──────────────────────────────────────────────────────────────┤
   │ Arquivos:  app.py (19×), auth.py (6×), merchant_payments.py  │
   │            (8×), transaction_graphql.py (4× via OCR)         │
   │ CWE:       CWE-89 (SQL Injection)                            │
   │ Severidade: CRÍTICA                                        │
   │ Detectado por: Semgrep (33) + OCR (10)                       │
   ├──────────────────────────────────────────────────────────────┤
   │ O QUE ACONTECE:                                              │
   │ Todas as queries SQL são construídas por concatenação direta  │
   │ de variáveis Python em strings f-string.                     │
   │                                                              │
   │ Exemplo em app.py:395:                                       │
   │   query = f"SELECT * FROM users                              │
   │            WHERE username='{username}'                       │
   │            AND password='{password}'"                       │
   │   user = execute_query(query)                                │
   │                                                              │
   │ Atacante pode enviar:                                       │
   │   username = "admin' --"                                   │
   │   password = "qualquer"                                       │
   │                                                              │
   │ Resultado: login aceito como admin.                          │
   │                                                              │
   │ POR QUE IMPORTA:                                             │
   │ SQL injection é o vetor #1 de vazamentos de dados na história│
   │ da web. Aqui, é trivial: um único POST /login com username  │
   │ malicioso bypassa toda a autenticação.                       │
   │                                                              │
   │ COMO CORRIGIR:                                               │
   │ Substituir TODAS as 33 ocorrências por queries parametrizadas:│
   │   cursor.execute("SELECT * FROM users                       │
   │                   WHERE username=? AND password=?",         │
   │                   (username, password))                       │
   │                                                              │
   │ Lista das linhas exatas: ver Seção 3.                        │
   └──────────────────────────────────────────────────────────────┘

   ┌─ #6 ─────────────────────────────────────────────────────────┐
   │ Debug mode exposto + container rodando como root             │
   ├──────────────────────────────────────────────────────────────┤
   │ Arquivo:   app.py (linha 2496), Dockerfile (linha 29)       │
   │ CWE:       CWE-489 (Active Debug Code) + CWE-250             │
   │ Severidade: ALTA                                            │
   │ Detectado por: Semgrep + OCR                                 │
   ├──────────────────────────────────────────────────────────────┤
   │ O QUE ACONTECE:                                              │
   │                                                              │
   │   1. app.py:2496 — app.run(host="0.0.0.0", debug=True)       │
   │      O debugger interativo do Werkzeug fica disponível em     │
   │      qualquer interface de rede acessível. Atacante pode     │
   │      forçar uma exceção para abrir o console e obter RCE     │
   │      (CVEs históricos do Werkzeug PIN bypass).                │
   │                                                              │
   │   2. Dockerfile:29 — CMD ["./start.sh"] sem USER directive    │
   │      Container roda como root. Se um atacante obtiver RCE,    │
   │      terá privilégios totais no container, facilitando        │
   │      escape ou pivot para o host.                             │
   │                                                              │
   │ POR QUE IMPORTA:                                             │
   │ Combinação perigosa: RCE trivial + root = comprometimento    │
   │ completo do sistema operacional do container.                │
   │                                                              │
   │ COMO CORRIGIR:                                               │
   │ a) app.py:2496: trocar para host="127.0.0.1",                │
   │    debug=os.getenv("FLASK_DEBUG","0")=="1"                   │
   │ b) Dockerfile: adicionar `USER nonroot` antes de CMD.        │
   └──────────────────────────────────────────────────────────────┘
